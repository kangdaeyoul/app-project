# 로그인 및 회사 범위 권한

현재 인증은 메모리 테스트 계정과 서버 세션을 사용한다. 기존 현장·견적·일일작업·자재·사진·정산 저장소와 데이터는 그대로 유지한다. 실제 Supabase Auth, 회원가입, 고객 포털, 비밀번호 찾기 메일은 연결하지 않았다.

## 교체 포트와 전역 상태

- `AuthProvider` / `AUTH_PROVIDER`: 비밀번호 인증, 세션 생성·해제, 현재 사용자, 회사 범위 사용자 관리. 현재 어댑터는 `MemoryAuthProvider`.
- `CompanyIdentityProvider` / `COMPANY_IDENTITY`: 검증된 세션을 서버의 회사·사용자·역할·현장 범위로 매핑한다. 요청 본문의 회사·역할·사용자 ID를 신뢰하지 않는다.
- `CurrentUser`, `CurrentCompany`, `UserRole`, `UserPermission`: 공통 타입. 실제 이름, 표시 이름, 연결 작업진행자 ID, 시스템 역할은 별도 값이다.
- `PermissionService`: 관리자/직원/작업진행자 권한, 허용 현장, 본인 참여 작업 검사 및 금액 필드 비노출.
- 웹 `AuthProvider` / `useAuth`: 현재 사용자·회사·임시 브랜드명·로그인 상태를 관리한다. 회사 이름과 로고는 서버 회사 설정에서 읽는다. 앱 이름은 `APP_BRAND`로 교체한다. 캐릭터에는 브랜드 로고를 넣지 않는다.

Supabase 연결 시 로그인/검증 어댑터를 교체하고 검증된 Supabase 사용자 ID를 내부 사용자 및 회사 소속에 연결한다. JWT의 임의 사용자 메타데이터를 회사 권한의 근거로 사용하지 않는다. 현재 동기 `CompanyIdentityProvider.resolve` 포트에는 검증 미들웨어가 확정한 신원을 제공하거나 서버 캐시/검증 계층을 둔다. 향후 영구 사용자 저장소와 세션 저장소도 분리해 구현한다.

## 정책

| 역할 | 현장 범위 | 금액 | 관리 |
| --- | --- | --- | --- |
| 관리자 | 현재 회사 전체 | 전체 | 사용자, 회사 설정, 감사로그, 기존 관리자 기능 전체 |
| 사내직원 | 명시적으로 허용된 현장 | 기본 비노출, 원가/손익/지급액 권한 개별 설정 | 일정, 견적 작성, 작업, 사진, 보고서, A/S |
| 작업진행자 | 대표/참여 일일작업, 현장 대표, 본인 A/S 배정 | 회사 금액 차단, 본인 정산 전용 API만 허용 | 본인 작업내용·시간·사용자재·사진, 완료 요청, 작업지시 읽음 |
| 고객 | 향후 고객-현장 관계로 제한 | 향후 공개 견적 DTO만 | 현재 로그인 및 API 접근 차단 |

직원의 `writeQuotes`, `editSchedule`, `internalCosts`, `siteFinance`, `workerPayments`는 관리자가 설정한다. 추가 금액 권한은 허용된 현장에만 적용한다. 원가 권한만으로 마진이나 현장손익을 노출하지 않는다. 견적 작성 권한이 없는 직원에게 견적 메뉴를 표시하지 않는다. 견적 승인·계약전환·삭제는 관리자 업무이다. 직원이 고객 판매단가를 수정해도 서버가 기존 내부 원가를 보존하며, 신규 견적의 비공개 원가는 기본 0이다. 내부 원가 없는 고객용 PDF/Excel DTO와 기존 출력 템플릿을 계속 사용한다.

작업진행자의 가용 현장 ID는 매 요청마다 회사 범위 현장/일일작업/A/S를 바탕으로 산출한다. 일일작업 조회와 변경은 해당 작업의 실제 대표 또는 참여자인지 별도로 확인한다. 작업진행자별 일정은 본인의 일정만 반환하고 다른 작업진행자 ID 지정은 차단한다. 기존 일일작업을 재사용하는 `/operational/daily-work/:id`는 작업내용·시간·사용자재·일반 작업상태만 변경한다. 클라이언트가 현장·대표·참여자 ID를 위조해도 배정을 바꾸지 않는다. 관리자확인완료 상태 변경과 확인 완료 기록 수정은 차단한다.

`/operational/sites`와 제한된 `/sites` 응답은 명시적인 현장 기본정보 필드를 사용한다. 제한된 사용자의 금융 전체 API, 자재 원가 DB, 다른 사용자 관리 등은 기본 거부한다. 회사 전체 데이터로부터 화면에서 필터하는 방식으로 권한을 구현하지 않는다. 사진, A/S, 알림센터는 기존 서비스의 본인 배정 검사도 적용한다. 본인 정산 API는 서버 세션의 작업진행자 ID로만 조회한다. 고객과 작업진행자에게 임의의 추가 관리자 금액 권한을 줄 수 없다.

## 세션 / 사용자 관리

- 쿠키: 무작위 256bit 세션 토큰, HttpOnly, SameSite=Lax, 루트 경로. 비밀번호와 토큰을 로컬 스토리지에 저장하지 않는다.
- 비밀번호: 개별 salt + scrypt 해시, timing-safe 비교. API/사용자 관리/감사로그에 해시나 비밀번호를 반환하지 않는다.
- 유지 ON: 서버·쿠키 30일. OFF: 브라우저 세션 쿠키, 서버 최대 8시간. 서버 재시작은 모든 메모리 세션을 만료시킨다.
- HTTPS에서는 `AUTH_SECURE_COOKIE=true`. 개발 모드 고정 테스트 계정은 실제 서비스 배포용 인증이 아니다.
- 실패 로그인은 계정별 5분 동안 10회 이후 제한한다. 외부 Origin의 변경 요청은 차단한다. 운영 프록시는 전달 Host 헤더를 신뢰할 수 있도록 관리해야 한다.
- 매 API 요청에서 최신 사용자 활성 상태·역할·회사 소속·현장 범위를 확인한다. 역할 변경과 비활성화는 기존 세션에도 즉시 적용된다.
- 웹은 로그인, 포커스, 10초 주기 및 관리자 저장 후 갱신한다. 메뉴는 최신 역할과 권한으로 재구성한다.
- 사용자 관리는 회사 범위 관리자만 가능하며 로그인 ID/이메일 중복, 작업진행자 연결, 허용 현장, 마지막 활성 관리자 유지 등을 검증한다. 회사 간 사용자 수정·이동은 현재 제공하지 않는다.
- 사용자 생성·역할/활성/범위 변경은 기존 감사로그에 비밀번호를 제외한 스냅샷으로 기록한다.

## PostgreSQL 이전

`company_users(company_id, auth_subject_id, login_id, email, name, display_name, role, active, worker_id)`와 `user_site_access(company_id,user_id,site_id)`, `user_permissions(company_id,user_id,permission)`, `auth_sessions`(현재 샘플 어댑터용)을 분리할 수 있다. Supabase에서는 비밀번호를 Auth가 관리하고 내부 DB는 회사 소속·권한만 보유한다. 고객은 별도 `customer_site_access`로 확장한다. 모든 연결은 회사 ID까지 포함한 FK와 서버 검사/RLS를 적용한다. 기존 `audit_logs`를 유지한다.

## 검증

인증 전용 테스트는 Nest 앱을 직접 생성하고 실제 세션 쿠키로 검증한다. 기존 도메인 회귀 테스트는 `test/test-app.ts`에서 명시적인 신뢰된 테스트 신원을 주입하며 배포 코드에는 우회 경로가 없다.

검증 대상: 익명/위조 신원/잘못된 비밀번호/비활성 로그인, 유지 쿠키/로그아웃/외부 Origin, 관리자 전체 조회, 직원 현장 범위 및 내부금액 비노출, 직원 견적 수정 시 원가 보존, 작업진행자 2명의 본인 현장/일정/작업/정산, 타인 일정/회사 손익 차단, 회사 간 현장/파일/사용자 격리, 역할 변경 및 비활성화 즉시 적용, 추가 금융 권한 부여/회수, 본인 작업 시작·종료·시간·사용자재 및 배정 위조·승인 차단.

최종 검증(2026-10-09): 전체 프로젝트 빌드와 TypeScript 검사 통과, API 테스트 69건 통과. Chromium에서 관리자·직원·작업진행자 2명·비활성 계정 로그인, 사용자 등록, 직원 견적 저장, 역할 변경 후 메뉴/API 차이, 본인 정산을 확인했다. PC 1440px / 모바일 390px 화면을 확인했고 브라우저 런타임 오류는 없었다. 실제 다운로드한 견적 PDF는 한글이 정상인 A4 3페이지이며, Excel의 갑지·기계·전기 시트와 기존 인쇄영역(A1:L40 / A1:I100 / A1:I76)이 유지되었다.
