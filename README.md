# 종로소방 통합 현장관리

PC 관리자 웹과 공통 API의 실행 가능한 초기 모노레포입니다. 모든 초기 현장/금액은 예시입니다. 등록·수정 데이터는 API 메모리에 저장되며 서버 재시작 시 초기 샘플로 돌아갑니다. 로그인, PostgreSQL, NAS, Flutter 앱은 아직 연결하지 않았습니다.

## 구성

- `apps/admin-web`: Next.js + React + TypeScript 관리자 웹
- `apps/api`: NestJS + TypeScript API
- `packages/shared`: 웹/API 공통 타입 및 메뉴 상수
- `docs`: 요구사항과 향후 데이터모델

## Windows에서 시작하기

Node.js 22 이상 LTS와 Git을 설치하세요. PowerShell 또는 명령 프롬프트에서 아래 명령을 실행합니다. PowerShell의 스크립트 정책으로 `npm.ps1` 실행이 차단되면 `npm` 대신 `npm.cmd`를 사용하세요.

```powershell
git clone https://github.com/kangdaeyoul/app-project.git
cd app-project
npm ci
npm run dev
```

관리자 웹은 `http://localhost:3000`, API 상태 확인은 `http://localhost:4000/api/health`입니다. Ctrl+C로 웹과 API를 함께 종료합니다. Linux/macOS도 동일 명령을 사용합니다. API를 먼저 준비하고 공통 패키지를 빌드하는 작업은 루트 개발 명령에 포함되어 있습니다.

```powershell
npm run build
npm test
npm run typecheck
```

빌드 결과를 실행하려면 두 터미널에서 각각 다음 명령을 실행하세요.

```powershell
npm run start -w @jongno/api
```

```powershell
npm run start -w @jongno/admin-web
```

포트 3000과 4000은 비어 있어야 합니다. 기본 API 주소를 변경하려면 웹 프로세스의 `API_URL`을 설정하세요. API 포트는 `PORT`입니다. 웹의 API 프록시 주소는 빌드 시 반영되므로 운영 빌드 전에 지정합니다.

```powershell
$env:API_URL = 'http://127.0.0.1:4100'
npm run dev -w @jongno/admin-web
# 다른 터미널에서 API를 실행합니다. 최초 실행 전 루트에서 npm run build -w @jongno/shared 실행
$env:PORT = '4100'
npm run dev -w @jongno/api
```

이 예시는 각 터미널의 환경변수를 분리하여 웹 3000/API 4100으로 실행합니다. 현재 인증 없는 샘플용이므로 외부 운영 서비스로 배포하기 전에 인증·권한 및 데이터 저장을 구현해야 합니다.

## API

- `GET /api/health`: 상태 및 sample 모드
- `GET /api/dashboard?month=2026-10`: 월별 현장과 대시보드 집계
- `GET /api/sites`: 전체 현장 목록 (`month=YYYY-MM`으로 일정이 겹치는 월 필터)
- `GET /api/sites/:id`: 현장 상세
- `POST /api/sites`: 현장 등록
- `PUT /api/sites/:id`: 현장 기본정보 전체 수정

대시보드는 월 생략 시 서울 시간 기준 현재 월이며 잘못된 `YYYY-MM` 값은 400을 반환합니다. 서버 시작 시 현재 월의 샘플 5건을 한 번 생성합니다. 월을 이동해도 현장 일정이 바뀌지 않습니다. 달력과 오늘 현장은 시작일부터 종료예정일까지(종료일 미정이면 시작일 하루) 표시합니다. 조회 월과 공사기간이 겹치는 현장이 월 집계에 포함되며, 여러 달에 걸친 공사는 각 해당 월에 전체 금액이 표시됩니다. 매출의 월별 분할은 하지 않습니다. 수금/지출/미지급/현장차익은 해당 현장들의 전체 기간 원장 누계입니다. 월별 현금 흐름 지표와 구분하세요.

현장 메뉴는 전체 목록, 현장명/거래처/주소 검색, 상태 필터, 등록, 상세, 수정을 제공합니다. 처음 등록 시 현장명과 시작일만 필수이며 금액은 기본 0원, 상태는 미배정입니다. 연락처는 자유 입력이며 대표 작업진행자는 등록된 작업진행자 목록에서 선택합니다. 상세에는 기본정보와 8개 탭이 있으며 개요에서 현장손익을, 수금·정산 탭에서 등록된 원장과 집계를 보여줍니다. 일일작업 탭에서 해당 현장의 작업을 등록·수정할 수 있으며 사용자재 등록과 현장 합계 조회가 가능하며 사진 조회도 가능하며 구매·작업비·기타경비 등록과 정산 상태 관리도 가능하며 일반 파일 등록은 후속 단계입니다. 공사금액은 VAT 포함 원 단위 정수입니다.

현장 입력 예시:

```json
{
  "name": "소방시설 개선 현장",
  "startDate": "2026-10-06",
  "contractAmount": 0,
  "status": "미배정"
}
```

선택 필드: `client`, `address`, `contactName`, `phone`, `description`, `endDate`, `managerId`. 수정은 기본정보 전체를 전송하는 PUT이며 선택 필드 생략 시 빈 값으로 처리됩니다. `id`, 입금액 및 작업진행자 미지급액은 등록·수정 입력에서 변경할 수 없습니다. 입금액과 작업진행자 미지급액은 수금/지출/지급 원장에서 계산하는 읽기 값입니다. 현장 입력으로 덮어쓸 수 없습니다.

등록·수정 후 대시보드도 같은 저장소를 조회하여 갱신됩니다. 달력과 오늘 현장, 대시보드 목록의 현장명을 누르면 상세로 이동합니다. API 장애 시 오류와 재시도 버튼을 표시합니다. 테스트는 날짜 경계, 집계, 등록→조회→수정→대시보드 반영, 월 경계 공사, 잘못된 입력과 누락 현장을 확인합니다.

## 확장 경계

`SitesRepository` 인터페이스와 `SITES_REPOSITORY` DI 토큰이 데이터 접근 경계입니다. PostgreSQL 연결 시 새 어댑터를 작성하여 `AppModule`의 바인딩을 교체하세요. 공통 계약은 `packages/shared`에 둡니다. 인증·파일 저장은 독립 모듈로 추가하고 NAS 경로나 비밀정보를 웹에 전달하지 않습니다. Flutter는 다음 단계에 추가합니다.

## 작업진행자 관리

작업진행자 메뉴에서 이름·표시명·연락처·업무 역할·메모·기본 작업 가능 상태를 등록/수정합니다. 이름과 표시명은 각각 필수이며 서로 별도로 저장합니다. 업무 역할(예: 소장)은 로그인 권한이 아닙니다. 향후 인증 사용자는 별도 모델에서 `workerId`로 연결합니다.

목록은 오늘 상태, 오늘 대표 배정 현장 수, 선택 월의 작업일수/지급예정액, 전체 미지급액을 제공합니다. 작업일수는 해당 월의 오늘까지 완료된 일일작업 참여 날짜의 고유 개수입니다. 지급예정액은 선택 월 지출일 기준 작업비·자재대납·기타 대납 원액이며, 미지급액은 전체 기간 지급의무에서 실제 기록된 지급액을 뺀 금액입니다. 현장 공사기간을 작업 실적으로 간주하지 않습니다. 일일작업은 일일작업 메뉴에서 입력하며 새 지출의 정산완료 여부는 기록할 수 있으며 실제 결제 연동은 후속 단계입니다.

상세 탭: 기본정보 / 일정 / 참여현장 / 작업이력 / 정산 / 휴무·불가시간. 날짜별 근무가능·휴무·오전불가·오후불가를 저장할 수 있으며 날짜별 상태가 기본 상태를 덮어씁니다. 같은 날짜 재등록은 수정으로 처리됩니다. 현재 근무 상태는 안내용으로 배정을 자동 차단하지 않습니다.

현장 대표 작업진행자는 활성 작업진행자 ID로 선택합니다. 현장에는 선택 시 표시명 스냅샷도 보관하여 이름 변경 및 삭제 후 기존 표시를 보존합니다. 삭제는 soft delete이며 새 배정에서는 제외되고 기존 배정/이력/정산은 유지됩니다. 삭제된 사람을 유지한 채 기존 현장을 수정할 수 있습니다. 대표 작업진행자를 변경하면 새 표시명 스냅샷을 저장합니다.

- `GET /api/workers?month=YYYY-MM&includeDeleted=true`: 목록/집계 (월 생략은 현재 월, 삭제 포함 기본 false)
- `GET /api/workers/:id?month=YYYY-MM`: 상세 및 원장/참여현장/근무 상태
- `POST /api/workers`, `PUT /api/workers/:id`: 기본정보 등록/전체 수정
- `DELETE /api/workers/:id`: 기록을 보존하는 삭제
- `PUT /api/workers/:id/availability/YYYY-MM-DD`: `{ "status": "휴무" }` 등 날짜별 상태

`WorkersRepository`는 기본정보·날짜별 상태·작업/정산 기록의 저장소 경계입니다. 현재 메모리 샘플 3명을 사용하며 API 재시작 시 초기화됩니다. 현장 입력의 `managerId`가 배정 기준이고 `manager`는 서버가 생성하는 역사 표시명입니다. 실제 DB는 연결하지 않았습니다.

## 일일작업 관리

일일작업 메뉴에서 작업일자·현장·대표 작업진행자·여러 참여 작업자·시작/종료시간·작업내용·특이사항·상태를 등록/수정합니다. 작업일자/현장/대표 작업진행자는 필수입니다. 같은 현장에 여러 날짜 또는 같은 날짜의 여러 기록을 추가할 수 있습니다. 현장 상세의 일일작업 탭은 현장 ID로, 작업진행자 상세의 작업이력 탭은 대표 또는 참여자 ID로 필터합니다.

작업예정 → 작업중 → 작업완료 상태로 시작/종료 버튼을 사용할 수 있습니다. 오늘 기록에만 서울 현재 시각(HH:mm)을 서버에서 기록하며 상태도 변경합니다. 지난 날짜의 시간은 수동 입력합니다. 작업완료 및 관리자확인완료는 시작·종료시간 모두 필요하며 시간/상태는 수정 화면에서 직접 변경할 수 있습니다. 관리자확인완료는 현재 단순 상태이며 인증/권한 검증은 아직 없습니다.

총 작업시간은 종료-시작의 분 단위 차이로 계산하고 휴게시간은 공제하지 않습니다. 자정 이후 종료는 날짜별 기록으로 분리합니다. 08:30~17:20은 530분(8시간 50분)입니다. 시작이나 종료가 미정이면 총 시간은 표시하지 않습니다.

- `GET /api/daily-work?siteId=...&workerId=...`: 전체/현장/작업진행자별 기록 (두 필터는 AND)
- `GET /api/daily-work/:id`: 단건 조회
- `POST /api/daily-work`, `PUT /api/daily-work/:id`: 등록/전체 수정
- `POST /api/daily-work/:id/start`, `POST /api/daily-work/:id/finish`: 오늘 현재 시각 기록

대표와 참여자는 작업진행자 ID로 연결하고 현장명/표시명 스냅샷을 보존합니다. 삭제된 작업진행자가 참여한 기존 기록은 그대로 조회·수정할 수 있으나 신규 배정은 불가합니다. 사용자재 건수는 연결된 사용자재 행 수로 계산합니다. 작업 전/후 사진 건수는 연결된 독립 사진 레코드 수로 자동 계산합니다.

작업진행자 목록의 작업일수는 일일작업의 작업완료·관리자확인완료 중 오늘까지의 월별 고유 참여 날짜로 집계합니다. 지급예정액/미지급액은 지출·지급 원장을 기준으로 집계합니다. 이전 가상 WorkerWork 정산 샘플은 현재 금융 집계에 포함하지 않습니다. 일일작업 시간을 자동으로 지급액으로 환산하지 않습니다.

`DailyWorkRepository`의 메모리 기록과 참여 관계는 API 서버 재시작 시 샘플 1건으로 초기화됩니다. 영구 저장을 제공하지 않습니다.

## 일일작업 사용자재

일일작업 등록 및 상세·수정 화면에서 자재명/규격/수량/단위/비고를 여러 줄 추가·수정·삭제할 수 있습니다. 일일작업 저장 시 모든 변경을 함께 반영하며 취소하면 저장하지 않습니다. 자재명·단위·양수 수량은 필수이고 수량은 소수점 3자리, 최대 1,000,000까지 지원합니다. 한 작업당 최대 200줄입니다.

사용자재 건수는 실제 연결된 사용자재 행 수이며 수량 합계가 아닙니다. 현장 상세의 자재·경비 탭에서 날짜별 사용 내역과 현장 총사용량을 확인합니다. 자재명·규격·단위가 같은 항목만 합산하며 m/개 등 서로 다른 단위는 환산하지 않습니다. 비고는 합계 기준에 포함되지 않습니다.

등록/수정 API의 `materials`는 `{id?, name, specification, quantity, unit, notes}` 배열입니다. 기존 행 수정 시 해당 행의 id를 보내고 신규 행에는 id를 생략합니다. 수정에서 배열을 생략하면 기존 사용자재를 보존하고 `[]`를 보내면 모두 삭제합니다. 기존 일일작업의 시작/종료 기능도 사용자재를 보존합니다. 일일작업의 현장/날짜 변경 시 자재 조회도 변경된 현장/날짜를 따릅니다.

`GET /api/daily-work/site-materials/:siteId`는 날짜별 `usages`와 합계 `totals`를 반환합니다. 구매·지출은 별도 expenses API에 등록합니다. 사용자재와 구매량은 자동 연동하지 않으며 원가배분·영수증 업로드는 아직 연결하지 않았습니다. API 메모리 자료는 서버 재시작 시 초기화됩니다.

## 작업 전·후 사진

저장된 일일작업의 상세·수정 화면에서 작업 전/후 사진을 여러 장 등록하고 설명·작업 위치·촬영일시·등록자를 수정하거나 사진 삭제 및 순서 변경을 할 수 있습니다. 사진 변경은 일일작업 기본정보 저장과 별개로 즉시 반영됩니다. 새 일일작업은 먼저 저장한 후 사진을 추가하세요. 현장 상세의 사진 탭은 날짜별로 사진을 모으며 전체/작업 전/작업 후/작업일자 필터와 확대 미리보기를 제공합니다.

PNG/JPEG/WebP를 장당 10MB, 한 번에 최대 20장 지원합니다. 원본 바이트를 변환하지 않고 임시 메모리 파일 저장소에 보관합니다. 사진 메타데이터와 파일 모두 API 재시작 시 사라지고 샘플 3장으로 초기화됩니다. 샘플은 실제 현장 사진이 아닌 예시 그림입니다. 촬영일시는 서울 시간으로 수동 입력하며 미입력도 가능하고 EXIF 자동 추출은 아직 없습니다. 등록자는 인증 전 단계의 수동 입력값입니다.

- `GET /api/photos?siteId=...&dailyWorkId=...&type=작업 전&workDate=YYYY-MM-DD`: 사진 조회 (필터는 AND)
- `POST /api/photos/upload`: multipart `files` 여러 파일과 `dailyWorkId`, `type`, `location`, `description`, `capturedAt`, `uploadedBy`
- `PUT /api/photos/:id`: 위치/설명/촬영일시/등록자 수정
- `PUT /api/photos/order`: `{dailyWorkId, type, ids}`로 해당 작업·구분의 전체 사진 순서 교체
- `DELETE /api/photos/:id`: 사진 메타데이터와 임시 원본 삭제
- `GET /api/photos/:id/file`: 원본 이미지 조회

`PhotoRepository`와 `FileStorage`가 별도 저장소 경계입니다. 이후 PostgreSQL 및 NAS 어댑터를 교체하고 인증·접근 정책, 스마트폰 촬영/EXIF, 필수사진 검사, 관리자 승인, 사진대지 PDF 서비스를 추가할 수 있습니다. 현장과 작업일자는 연결된 일일작업에서 조회하므로 일일작업의 현장/날짜 변경도 사진 조회에 반영됩니다.


## 자재구매·경비·대납

자재·경비 메뉴에서 현장 필수/일일작업 선택 연결로 지출 등록·상세·수정·삭제 및 현장/지출유형/정산상태 필터·검색을 제공합니다. 현장 상세는 사용자재 / 구매자재 / 작업비 / 기타경비를 나누어 표시합니다. 구매 기록은 기존 사용자재를 변경하거나 사용량/재고를 차감하지 않습니다.

유형은 회사 직접 자재구매 / 작업진행자 대납 자재구매 / 작업비 / 기타경비입니다. 결제방법과 증빙유형은 등록 화면의 선택값을 사용합니다. 수량은 양수(최대 1,000,000, 소수점 3자리), 공급가액/VAT는 0 이상 원 단위 정수입니다. 공급가액은 단가가 아닌 전체 공급가액이며 합계금액은 서버가 공급가액+VAT로 계산합니다. VAT는 수동 입력하여 면세/실제 증빙액을 기록할 수 있습니다.

대납 자재구매의 결제방법은 작업진행자 대납입니다. 회사 직접 자재구매는 회사 결제수단을 사용합니다. 기타경비도 작업진행자 대납 결제방법을 사용할 수 있으며 대납 여부는 유형/결제방법에서 결정합니다. 대납 및 작업비는 작업진행자 ID가 필수이고 당시 표시명 스냅샷을 저장합니다. 작업비는 대납 환급과 구분하며 회사 지급수단을 선택합니다. 삭제된 작업진행자를 새 기록에 선택할 수 없지만 기존 지출/정산 기록은 유지·수정할 수 있습니다.

회사 지출의 정산완료는 기록 상태입니다. 작업비·대납의 정산완료를 지출 화면에서 처리하면 해당 지출 잔액의 지급 원장 기록을 추가합니다. 일부 지급은 정산 메뉴에서 등록하며 지급 상태는 원장에서 계산합니다. 정산일/지급일은 지출일 이후여야 합니다. 회사 결제수단 역시 기록값이며 은행/카드/세금계산서 API를 호출하지 않습니다. 영수증 업로드 없이 `receiptFileKey` 참조 필드만 준비했습니다.

현장 합계는 선택 현장의 전체 기록 기준이며 유형/검색/정산 필터로 합계 범위가 바뀌지 않습니다. 직접 자재구매, 대납, 작업비, 기타경비, 총 현장지출을 표시합니다. 기타경비 대납은 대납 및 기타경비 소계에 모두 포함되지만 총 현장지출은 각 기록을 한 번만 합산합니다. 미정산 지급의무도 지출 원액에 포함됩니다.

작업진행자 상세 정산 탭은 현장별 작업비/자재대납/기타정산과 지급예정/완료/미지급액을 표시하며 전액·일부 지급 및 지급 기록 취소를 제공합니다. 전체 기간 합계와 조회 월 합계를 구분합니다. 대시보드, 현장 기본정보, 작업진행자 목록은 같은 원장 데이터를 사용합니다. 이전 가상 원장 금액을 더하지 않습니다. S001의 지출은 669,000원이며 W001의 지급예정액은 537,000원입니다.

- `GET /api/expenses?siteId=...&workerId=...`: 필터는 AND. `items`, 현장 `totals`, 지급의무 `workerTotals` 반환
- `GET /api/expenses/:id`: 단건
- `POST /api/expenses`, `PUT /api/expenses/:id`: 등록/전체 수정
- `DELETE /api/expenses/:id`: 지출 및 연결 정산 관계 삭제

연결 일일작업은 같은 현장이어야 합니다. 지출이 연결된 일일작업의 현장을 바꾸려면 먼저 지출의 일일작업 연결을 해제해야 합니다. `ExpensesRepository` DI 경계에서 지출·수량/단위·작업진행자 지급 관계를 분리해 메모리로 보관하며 API 재시작 시 8개 지출 샘플로 초기화됩니다. Windows 실행 명령은 위와 같고 새 외부 서비스 설정은 필요하지 않습니다.


## 수금·미수·지급·현장손익

현장 상세 수금 탭 및 관리자 정산 메뉴의 수금·미수 화면에서 다건 수금 등록·수정·삭제를 제공합니다. 입금일, 현장, 양수 원 단위 금액, 계좌이체/카드결제/현금/기타, 입금자명 또는 거래처, 비고를 기록합니다. 총 입금액은 모든 수금내역의 합계이고 미수금은 현장 계약금액−총 입금액입니다. 초과 입금도 기록할 수 있으며 미수금은 음수 그대로 표시합니다.

관리자 정산 메뉴에는 작업진행자 지급 / 수금·미수 / 현장손익 화면이 있습니다. 작업진행자 지급 화면은 지급의무가 없는 사람도 0원으로 보여주는 전체 작업진행자 요약, 현장별 정산내역, 지급 기록 목록을 제공합니다. 현장/작업진행자 상세에서 같은 지급 화면을 사용할 수 있습니다. 삭제된 작업진행자의 기존 지급대상도 보존됩니다.

지급예정액은 작업비 + 대납 자재비 + 기타경비 대납의 원액입니다. 지출 한 건이 정산 항목 하나이며, 지급은 현장+작업진행자별 잔액에 배분합니다. 지급완료 처리 버튼은 서버 최신 잔액 전액을 기록하고 일부 지급 버튼은 입력 금액을 기록합니다. 지급일은 서울 오늘로 기본 설정하고 수정할 수 있습니다. 지급액/상태는 원장 합계에서 미지급/일부지급/지급완료로 계산합니다. 기존 잔액을 넘는 지급이나 이미 완료된 전액 지급 재요청은 거부합니다. 실제 송금은 실행하지 않습니다.

지급은 지출일·ID 순서로 남은 지급의무에 배분합니다. 지급일이 배분 대상 지출일보다 빠르면 저장하지 않습니다. 지급 원장 기록을 취소하면 배분과 미지급액이 복원되며 실제 은행 송금을 취소하지 않습니다. 지급 기록이 있는 지출은 삭제, 현장/작업진행자/유형 변경, 지급액 미만으로 금액 축소, 지급일 이후로 지출일 변경을 거부합니다. 먼저 관련 지급 기록을 취소해야 합니다. 미정산 플래그만 바꾸어 지급완료를 되돌릴 수 없습니다.

월 발생 지급예정액은 지출일 기준, 월 지급액은 지급일 기준입니다. 해당 월 발생분 잔액은 그 달 지출의 현재 미지급 잔액이며 두 월 합계를 단순히 빼는 값이 아닙니다. 현장별 원장과 전체 기간 합계에는 모든 날짜의 기록을 포함합니다.

현장차익 = 계약금액 − 회사 직접 자재구매 − 대납 자재구매 − 작업비 − 기타경비입니다. 미지급 지출도 발생 원액으로 한 번만 포함하고 지급 원장을 다시 비용으로 더하지 않습니다. 실제 입금/지급 여부와 현장차익은 구분됩니다. 회사 전체 세금·보험·고정비를 반영한 회계상 순이익이 아닙니다.

샘플 S002(혜화 상가 감지기 교체): 계약 5,500,000원, 입금 4,000,000원(2건), 미수 1,500,000원, 직접 자재비 820,000원, 자재대납 310,000원, 작업비 1,200,000원, 기타경비 120,000원, 총지출 2,450,000원, 현장차익 3,050,000원입니다. W003의 지급예정/미지급액은 1,510,000원입니다.

- `GET /api/sites/:id/finance`: 현장 수금·지출·차익·미지급 요약
- `GET /api/payments-received?siteId=...`: 현장 수금 목록
- `POST /api/payments-received`, `PUT /api/payments-received/:id`, `DELETE /api/payments-received/:id`: 수금 등록·수정·삭제
- `GET /api/settlements?siteId=...&workerId=...&month=YYYY-MM`: 현장/작업진행자별 정산, 지급 기록, 전체/월 합계 (필터 AND)
- `POST /api/worker-payments`: `{siteId, workerId, paymentDate, amount, notes}`. `fullPayment:true`면 최신 잔액 전액
- `DELETE /api/worker-payments/:id`: 지급 원장 기록과 배분 취소

`FinanceRepository`는 수금·지급·지출별 지급 배분의 메모리 저장소 경계입니다. 재시작 시 수금 샘플 6건과 지급 0건으로 초기화됩니다. 금융 입력/집계는 JS 안전 정수 범위를 검사하며 DB 연결, 은행·카드사·홈택스 연동은 없습니다. Windows 실행/검증 명령은 기존과 동일합니다.


## 세금계산서·증빙 관리

관리자 정산 메뉴의 **세금계산서·증빙** 화면에서 매출 / 매입 / 지출 증빙 / 작업진행자 계산서를 구분해 관리합니다. 현장 개요·수금 탭에는 매출 발행상태와 관리 버튼을, 자재·경비 탭에는 지출별 증빙유형/매입 수취상태와 관리 화면을 표시합니다. 작업진행자 정산 화면에는 현장별 계산서 상태와 수정 기능을 제공합니다.

이번 단계는 현장당 매출 관리기록 1개, 지출당 매입 관리기록 1개, 현장+작업진행자 정산별 상태 1개입니다. 별도 저장값이 없으면 매출은 미발행, 세금계산서 유형 지출은 미수취, 작업진행자 정산은 미발행으로 조회합니다. 등록 화면을 따로 요구하지 않고 해당 행의 계산서 수정에서 최초 저장도 합니다. 향후 분할/다건 세금계산서는 독립 invoice_id와 관계 테이블로 확장할 수 있습니다.

매출은 거래처, 공급가액/VAT/자동 합계, 미발행/발행완료/발행불필요, 발행일, 승인번호, 비고를 관리합니다. 최초 금액은 VAT 포함 현장 계약금액에서 공급가액=floor(계약금액×10/11), VAT=차액으로 계산한 예시이며 실제 발행액으로 수정할 수 있습니다. 수금은 같은 현장의 여러 수금 ID를 선택 연결할 수 있으며 계산서 금액과 수금액은 별도로 보관합니다. 연결된 수금의 삭제/다른 현장 이동은 먼저 계산서 연결을 해제해야 합니다.

매입은 세금계산서 증빙유형인 지출/구매를 기준으로 공급업체, 지출의 공급가액/VAT/합계, 미수취/수취완료/해당없음, 수취일, 승인번호, 비고를 관리합니다. 매입 금액은 지출과 같아야 하고 지출 화면에서 변경합니다. 수취완료 계산서가 있는 지출은 현장/금액/공급업체/증빙유형 변경 및 삭제를 막습니다. 먼저 계산서 상태를 바꾸어야 합니다. 다른 증빙유형은 매입 계산서 수취상태가 해당없음이며 지출 증빙 목록에서 확인합니다.

지출 증빙 화면의 증빙유형 필터와 **증빙없음 / 세금계산서 미수취** 필터로 누락 기록을 찾습니다. 매출 미발행, 매입 미수취, 증빙없는 지출, 작업진행자 정산 계산서 미수취 건수를 표시합니다. 작업진행자 계산서는 미발행/발행완료/해당없음을 수동 기록하며 미발행을 미수취 경고로 셉니다. 건수는 현장+작업진행자 정산 그룹 수입니다. 개별 매입 수취상태 및 지급상태와 자동으로 바꾸지 않습니다.

발행완료/수취완료 상태에는 날짜와 승인번호가 필수입니다. 승인번호는 수동 관리값이며 국세청 승인 여부를 확인하지 않습니다. 사업자등록번호, 상호, 대표자, 주소, 업태, 종목, 이메일을 공급자·공급받는자 정보로 선택 입력할 수 있습니다. 홈택스/전자세금계산서 API 호출이나 실제 발행·수취·금융원장 변경은 수행하지 않습니다.

대시보드 경고는 조회 월과 공사기간이 겹치는 현장 기준이며 증빙 화면 건수는 선택 현장/작업진행자 범위입니다. 화면의 검색/상태 필터로 요약 건수는 바뀌지 않습니다. 초기 샘플은 매출 미발행 4건, 매입 미수취 5건, 증빙없는 지출 2건, 작업진행자 정산 계산서 미수취 2건입니다. S003 매출과 E001 매입은 완료 예시이며 승인번호에 SAMPLE을 명시합니다.

- `GET /api/invoices?siteId=...&workerId=...`: 매출·매입·증빙·작업진행자 계산서와 경고 집계 (필터 AND)
- `GET /api/invoices/sales/:siteId`: 현장 매출 계산서
- `PUT /api/invoices/sales/:siteId`: 매출 기록 저장 및 같은 현장 수금 연결
- `PUT /api/invoices/purchases/:expenseId`: 매입 기록 저장
- `PUT /api/invoices/workers/:siteId/:workerId`: 정산 계산서 상태 저장

`InvoicesRepository`는 메모리 저장소 경계입니다. 서버 재시작 시 상태와 사업자정보는 초기 샘플로 돌아갑니다. 외부 서비스 설정이나 추가 패키지 없이 기존 Windows 실행 명령을 사용합니다.

### 사진대지 PDF

현장 상세 → **사진** 탭의 사진대지 영역에서 전체/작업일자/작업 전·후/개별 사진을 선택합니다. 문서 제목(기본 `공사 사진대지`), 회사명, 공사내용, 작업기간, 작성일과 작업진행자·사진번호·촬영시간 표시 여부를 설정한 뒤 **사진대지 미리보기** → **PDF 생성** 순서로 다운로드합니다. 옵션 변경 시 미리보기를 다시 생성합니다. 기본 파일명은 `현장명_공사사진대지_작성일.pdf`입니다.

- 작업 전/후 비교형: 같은 작업일자와 입력된 위치 기준으로 순서대로 짝짓습니다. 날짜나 위치가 다르거나 위치가 비어 있으면 짝을 강제로 만들지 않으며, 남는 사진도 출력합니다.
- 페이지당 4장 / 페이지당 6장: 2열의 A4 세로 문서입니다. 사진은 비율을 유지하고 모든 선택 사진을 출력합니다. 긴 설명과 위치는 별첨으로 전체 내용을 보존합니다.
- 미리보기는 실제 생성된 PDF를 PDF.js로 렌더링하며, 이전/다음 페이지로 확인합니다. 브라우저 내장 PDF 뷰어 없이도 표시되고 새 창 링크도 제공합니다. 웹 `predev`/`prebuild`가 설치된 PDF.js worker를 public으로 복사하므로 Windows에서도 같은 명령으로 실행합니다.
- 기존 사진과 일일작업의 연결 및 작업진행자 표시명 스냅샷을 사용합니다. 원본 파일은 수정하지 않으며, PDF용 이미지 변환만 수행합니다. 촬영일시와 기본 작성일은 서울 시간 기준입니다.
- Nanum Gothic 한글 TTF를 문서에 부분 삽입합니다. 인터넷 없이 출력할 수 있으며 폰트와 OFL 라이선스는 `apps/api/fixtures/fonts`에 포함되어 있습니다. 배포 시 API의 `dist`와 함께 `fixtures`도 유지하세요.
- 한 번에 최대 60장. 임시 PDF 저장소는 최대 20개·30분 동안 보관하며 서버 재시작 시 초기화됩니다. 원본 사진 임시저장소와 별도의 `PhotoReportStorage` 인터페이스를 사용합니다. 논리 저장 키는 `현장ID/05 현장사진/사진대지/생성ID/파일명`이며, 향후 NAS 어댑터로 교체할 수 있습니다. 현재 보관 파일 조회 UI는 제공하지 않고 생성 응답으로 바로 다운로드합니다.
- API: `POST /api/sites/:siteId/photo-reports/preview` (저장하지 않는 inline PDF), `POST /api/sites/:siteId/photo-reports/generate` (임시저장 + attachment PDF). JSON 출력 옵션은 공통 `PhotoReportOptions` 타입을 사용합니다. 생성 응답의 `X-Report-Storage-Key`는 URI 인코딩된 저장 키입니다.
